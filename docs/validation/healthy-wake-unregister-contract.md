# Healthy wake callback unregister: source contract

The pinned mpv revision is [`01e2533f3143b8940857ca419b0b367f583e05ca`](https://github.com/mpv-player/mpv/tree/01e2533f3143b8940857ca419b0b367f583e05ca). In its [`player/client.c`](https://github.com/mpv-player/mpv/blob/01e2533f3143b8940857ca419b0b367f583e05ca/player/client.c#L317-L351), the callback and userdata belong to one `mpv_handle` and are protected by `wakeup_lock`. The two source-level callback invocation sites are `wakeup_client`, which invokes the registered callback while holding that lock, and `mpv_set_wakeup_callback`, which invokes a newly installed non-null callback while holding the same lock.

**Source inference:** for the same live handle, a null callback setter returning after acquiring that lock waits for a callback already inside either invocation path; a producer waiting before entry subsequently sees the cleared callback. This assumes no concurrent re-registration, no concurrent handle destruction, a normally returning callback, and the pinned implementation's behavior. The setter must pass null userdata too if the caller intends to clear both fields. The public API documentation does not explicitly promise this unregister-return barrier.

The [client API contract](https://github.com/mpv-player/mpv/blob/01e2533f3143b8940857ca419b0b367f583e05ca/include/mpv/client.h#L1673-L1709) describes a single callback slot, foreign-thread and potentially reentrant delivery, prompt normal return, and prohibits client API calls from inside the callback. A null setter return does not drain Qt work already queued by a callback, settle a worker fence, or establish application target lifetime. Handle and callback storage must remain alive through unregister; queued deliveries and hooks require separate closure.

**`NativeWakeupUnregisterBarrier = BUILDER_SOURCE_QUALIFIED`** for Windows x64, the pinned source revision above, and DLL SHA-256 `5c5c9d094859bdc60b8b27b2d832db8fa8c2e487efbd35f5aea5afe6960dad39`. The accepted trusted-builder source qualification is limited to the same-live-handle, no concurrent re-registration or destruction, normal-return and no-client-API assumptions above, with every invocation covered by the audited lock. This is distinct from the render-update callback barrier and its separate registration and lock.

The existing `HealthyWakeBinding` injected tests do not establish native runtime qualification. The default runtime barrier remains disabled until actual loaded-module identity and controlled staged-byte verification pass. Queued Qt wakeups, Player event-drain closure, worker termination and native retirement require separate evidence. This record makes no native execution, playback, CI or retirement-completion claim.
