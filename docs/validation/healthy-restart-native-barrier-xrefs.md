# Native callback barrier: bounded binary cross-reference

**Status remains UNQUALIFIED.** This is additional static evidence for the exact Windows DLL SHA-256 `5c5c9d094859bdc60b8b27b2d832db8fa8c2e487efbd35f5aea5afe6960dad39`; it does not establish the complete callback invocation graph or the module loaded by a future process.

The [prior follow-up](healthy-restart-native-barrier-followup.md) identified setter helper thunks but did not map their imports. Read-only PE import-table inspection now maps preferred VA `0x185f8f1f0`, via IAT RVA `0x72c8160`, to `KERNEL32.dll!AcquireSRWLockExclusive`, and `0x185f8f2c0`, via IAT RVA `0x72c86f8`, to `KERNEL32.dll!ReleaseSRWLockExclusive`. The exported setter passes `ctx + 0x50` to those thunks around its callback/context stores and optional immediate indirect call.

A separate routine at preferred VA `0x1810612f0` also acquires the first thunk on `ctx + 0x50`, reads the callback and context at `ctx + 0x60` and `ctx + 0x68`, conditionally makes an indirect call, invokes `KERNEL32.dll!WakeAllConditionVariable` through IAT RVA `0x72c8920`, and tail-calls the release thunk with the same lock address. This supports a shared exclusive-lock interpretation for these two observed paths. These are static preferred addresses, not runtime addresses, and an indirect-call target and actual loaded module were not observed.

A bounded byte scan of the `.text` section for relative `E8`/`E9` branches to the second routine found no candidates. That scan is not an exhaustive cross-reference proof: it cannot exclude function-pointer calls, other indirect control flow, inlining, or accesses reached with different register/layout derivations. The unexported routine has no independently verified symbol in this evidence. The remaining gap is a complete, independently reviewed binary control-flow and alias analysis proving every callback invocation uses the same lock, including any alternate or inlined path. The earlier release/build provenance gap also remains. Until either complete route and later loaded-module verification is established, no native free or positive retirement ACK may rely on this observation.

Inspection used the installed MSVC dumpbin and a bounded local PE import/branch reader against the file as data. The DLL was not loaded or executed; no build, installation, CI, GUI or playback occurred. The import reader is retained in task proof storage for independent review.

The exact commands were `dumpbin /nologo /exports <DLL>`, `dumpbin /nologo /headers <DLL>`, and `dumpbin /nologo /disasm /range:0x181061530,0x181061580 <DLL>` and `/range:0x1810612F0,0x181061332 <DLL>`, using the tool and DLL hashes in the prior follow-up. The lock and unlock thunks were separately disassembled at `0x185F8F1F0` and `0x185F8F2C0`; the retained `deps/w863-proof/imports.py` maps their IAT entries from the PE import table and scans the code section for direct relative branches. Key setter instruction bytes are `48 8d 71 50` (lock address), `e8 a2 dc f2 04` (acquire thunk), `49 89 7e 60` and `49 89 5e 68` (callback/context stores), `ff 15 81 1e 26 06` (indirect callback dispatch), and `e9 48 dd f2 04` (release thunk). The second routine's corresponding bytes are `48 8d 71 50`, `e8 eb de f2 04`, `48 8b 47 60`, `48 8b 4f 68`, `ff 15 d0 20 26 06`, and `e9 8d df f2 04`.

A read-only inventory of the local SDK found no `.pdb`, `.debug`, `.dbg` or `.map` files. The retained pinned vendor archive's 7-Zip listing contains only `include/mpv` headers, `libmpv.dll.a` and `libmpv-2.dll`; it contains no separate symbol or recipe file. This inventory does not prove that no external symbols or build records exist.
