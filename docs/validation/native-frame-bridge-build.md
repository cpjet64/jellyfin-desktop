# Native frame observation bridge: source and build boundary

The bundled mpv source must match commit `01e2533f3143b8940857ca419b0b367f583e05ca` and the blob and SHA-256 identities in `patches/mpv/source-identity.json` before applying the adjacent patch. A build must use the repository's authorized native or remote build path, preserve the original source and toolchain, and record the patch hash, compiler and dependency identities, exact configuration, exported symbol, and resulting library hash. No build or packaging is authorized by this document. The existing SDK and installed/system libraries have not been shown to contain this bridge.

Resolve `mpv_render_context_render_recovery_v1` from the same loaded module as the other mpv functions. If the symbol is missing or its versioned call fails, report the capability unavailable and do not infer equivalent evidence from a pending-frame query. The shared application header defines the v1 structure. The patch's private upstream header has the same field order and widths; compare these explicitly during integration. The caller initializes size and version and must serialize calls under the existing mpv render API rules.

The player stamps a queued frame with its native playlist entry, current video-reset discontinuity, source-frame serial and source media timestamp before handing it to the VO. The VO's existing frame-reference copy retains the stamp, including on redraw. IDs outside `1..INT64_MAX`, a serial overflow, a missing entry or an invalid timestamp cannot yield a valid record. A successful non-skipped render publishes the stamp of the frame selected by that same render call. A repeated redraw can produce a later render serial but keeps its source-frame serial. Render success is not a Qt submission, swap, or visible-picture guarantee.

Before production use, independently verify frame stamping and reset on load and seek; copied and retained frames; dummy, skip, target-error and render-error paths; old-frame redraw during a replacement load; and rollover and invalid identifiers. Verify that Qt binds the exact successful record to its own submission and swap, and that superseded intent and expired attempts cannot resume playback. Sparse or still-image content must not be judged stalled solely because source serial does not advance. Finally, build and exercise the exact bundled library and packaged application using the separately authorized acceptance plan; source and apply checks do not prove those outcomes.

## Reproducible build inputs and gates

The current Windows setup and CI obtain prebuilt libmpv archives; they do not define a source build of this pinned mpv revision. The compiler, Meson, Ninja, FFmpeg and other dependency versions, configure options, CPU baselines and dependency provenance for a replacement library are not established here. A reproducible binary recipe is therefore **blocked** until those inputs and an authorized Windows-capable build environment are selected and pinned. Do not copy the current binaries into a new package and label them bridge-capable, and do not assume one CPU build covers both the primary and fallback paths.

The selected historical provider, concrete floating inputs and bounded unresolved items are recorded in [the provider audit](../../patches/mpv/build/provider-audit.md). This is an investigation record, not a complete lock or authority to run its update or build scripts.

Once those inputs and execution are separately authorized:

1. Create isolated source, build and staging directories. Record their locations and free-space headroom. Verify the full mpv commit and the source blobs and SHA-256 values in the manifest, then apply the pinned patch with a checked, recorded patch operation. Recheck the patched tree and preserve the exact patch and source identity record.
2. Record the exact tool and dependency versions, hashes, compiler target and CPU flags, environment allowlist, complete Meson configuration and dependency resolution. Configure the pinned Meson project with a shared library and `libmpv` enabled; `cplayer` may be disabled only if the qualified recipe confirms it is unnecessary. Build primary and fallback variants according to independently qualified CPU baselines. Preserve complete bounded build logs and resulting DLL, import library and dependency hashes for each variant.
3. Verify the exported symbol `mpv_render_context_render_recovery_v1` in each exact DLL and test its v1 call against the matching build. The pinned Meson source requests hidden default visibility, so the patch's `MPV_EXPORT` declaration is required; its actual Windows export must be confirmed from the artifact. The new mpv header is not included in the pinned Meson install-header list: preserve it with the build evidence and use the matching application header rather than assuming an SDK install copied it. Validate C and C++ inclusion in both orders, field widths, offsets, size, version and calling convention.
4. Stage each qualified DLL and its dependencies in a fresh package candidate without overwriting the global SDK. Verify the selected primary and fallback identities and resolve the optional symbol from the already loaded mpv module used by the existing API. A missing symbol, mismatched ABI, bad version or failed call must remain unavailable; do not load a second DLL to manufacture the capability.
5. Exercise source-aware frame attribution and renderer submission/swap tests, then the separately authorized packaged Windows acceptance. Bind every result to source commit, patch, toolchain, dependency and artifact hashes. Preserve failure and rollback evidence; a successful source build alone does not establish visible playback recovery.

For the initial load-at-target flow there is no separate pre-frame discontinuity query in this bridge. The sole event consumer may latch the discontinuity from a valid frame for the accepted native entry only while its load/event epoch remains current, and must carry that exact record through the associated submission and swap. Conflicting starts, ends, resets, seeks, intent changes or attempt expiry invalidate that association. A later seek needs its own qualified discontinuity boundary; the first matching frame is not independent proof of event correlation.

## Source-lock and artifact contract in progress

`patches/mpv/build/recovery_lock_preflight.py` checks an independently approved lock SHA-256, the selected provider and mpv commits, the three exact committed bridge patches, the approved Rust components, candidate feature-root source identities, declared nested/offline completeness, variant targets, features and export requirements. It does not fetch sources or run a build. Its completeness fields are assertions in the reviewed lock, not independent proof that every dependency or download has been discovered. The current repository does not contain a complete lock, and the source preflight therefore cannot establish build readiness.

`offline_inputs.py` is a preliminary, unexecuted input-byte gate. It requires a complete lock and separately approved inventory digest, and checks contained non-linked files. Source records have `{name, path, sha256, size}`; archives are also compared with their source-lock SHA-256 and/or SHA-512. A `materials` array of `{name, path}` records binds the four selected Rust components and every registry crate in the lock-bound subrandr inventory to their individual checksums. It expressly rejects Git sources until bundle, commit, tree and selected submodule verification is implemented. It does not establish Cargo completeness beyond that selected inventory, host-tool identities, provider fetch removal, offline configuration or build orchestration. This gate must not launch a build.

`recovery_artifacts.py produce` first requires that preflight, then records actual staged file hashes and the locked configuration in a new versioned manifest; it does not run a compiler or claim the declared features were exercised. On Windows, `verify` additionally requires separately approved lock and manifest SHA-256 values and a dumpbin executable whose hash is in the approved lock. It checks both x86-64 variants, contained paths and file hashes, AMD64 headers, required public and private DLL exports, import-library mpv symbols, and declared static DLL dependencies. The optional packaged-directory check compares both installed DLL bytes with the approved manifest. Loader-only dynamic dependencies, binary feature behavior and visible recovery still require independent evidence.

The current source contract permits only the explicit `windows-static-nonsystem` profile: both variants must declare an empty non-system runtime DLL closure, and every direct static import must be in the finite reviewed Windows-system-name list. An unlisted API-set name is rejected until explicitly reviewed; no prefix wildcard grants system status. Verification rejects system-name DLLs shadowed beside the staged mpv DLL or at the package root. This policy must not be met by disabling requested playback features: if the actual build needs a non-system runtime DLL, the profile and packaging design need a separately reviewed change.

The Qt source identity set is the exact selected Base, Quick and shared-ABI production path set, not any two files under `patches/qt`. Each source record contains its canonical-text SHA-256 and Git blob identity. For these tracked text sources only, CRLF is normalized to LF and lone carriage returns are rejected before both identities are computed; the source test contract covers LF/CRLF equivalence and changed tokens. DLLs, import libraries, Qt kit artifacts, configuration evidence and packaged binaries always use raw file-byte hashes without text normalization.

For an explicitly requested recovery artifact, set `JELLYFIN_RECOVERY_ARTIFACT_REQUIRED=1` and provide `JELLYFIN_RECOVERY_LOCK`, `JELLYFIN_RECOVERY_LOCK_SHA256`, `JELLYFIN_RECOVERY_MANIFEST`, `JELLYFIN_RECOVERY_MANIFEST_SHA256`, `JELLYFIN_RECOVERY_DUMPBIN`, `JELLYFIN_RECOVERY_QT_ROOT`, `JELLYFIN_RECOVERY_PYTHON`, and the separately reviewed lowercase `JELLYFIN_RECOVERY_PYTHON_SHA256`. Configure also requires an absolute `Python3_EXECUTABLE` resolving to the same reviewed path; CMake hashes that executable before invoking it in isolated mode. On the reviewed workstation, `C:/Python314/python.exe` was observed with SHA-256 `7ca24f26d6e3f463419ee4f537ddd3acd312c38fe45e678cce08572f26a8bd1a`; another host requires its own observed and reviewed identity. The approved executable identity, lock digest and manifest digest are captured at configure and checked again during packaging. The setup, CI mpv acquisition and bundle paths then require verification of already staged custom primary and fallback artifacts and do not silently download stock replacements. The kit manifest also binds Qt 6.9.3 source-patch identities, its build-configuration file, every installed header and CMake package file, the Core/Gui/Quick/OpenGL release DLLs and import libraries, and the Windows platform plugin. Configure-time verification compares those files with the actual configured mpv library and include directory, Qt package, imported target libraries and include paths. Packaging checks both installed mpv DLLs and the relevant installed Qt DLLs and plugin against that manifest.

Only a successful normal bundled Windows configure-time check sets the private `MpvQt` target definition `JELLYFIN_VERIFIED_RECOVERY_KIT=1`. Unsupported configurations, ambiguous paths, missing artifacts and failed checks stop an explicitly requested recovery build; no definition is set for stock builds. The renderer must still require its actual same-module bridge exports and attributed frame pipeline. This build flag is not runtime binary authentication: the assembled application, deployed loader paths and release policy must retain the exact verified artifacts and prevent an unverified runtime replacement from being treated as release proof. These source changes and their test source have not been executed or qualified.

## Runtime resolver source

`patches/mpvqt/runtime/RecoveryFrameBridge.{h,cpp}` supplies an optional resolver for the normal linked mpv API. Its owner keeps the actual mpv module and render context alive throughout resolver use, serializes render calls and destruction on the render thread, and links the platform dynamic-loader library where needed (`${CMAKE_DL_LIBS}` on the normal bundled target). The helper does not support mpv's C-plugin dynamic-symbol mode. On Windows it locates the image containing the existing render function without changing its reference count, checks the standard export, then accepts the extension only if its address belongs to that same image. On Linux and macOS it identifies the existing image, obtains a local `RTLD_NOLOAD` handle, confirms the standard address and extension image base, and retains that handle until destruction. Missing or unverifiable capability remains unavailable. The checks establish image consistency, not binary authenticity or artifact provenance.

For each call the helper uses either the verified extension once or, when unavailable, the standard render once. It never retries a failed extension call through standard render. The result preserves the native return code and emits an invalid observation for a failed or skipped render, a malformed record, or ordinary playback through an unpatched library. Capability availability does not itself mean a frame was rendered. The renderer must bind a valid result to the exact Qt submission and swap before it can contribute to recovery.

Before publishing a source serial, the helper requires finite media PTS in the inclusive interval `0 <= PTS <= double(INT64_MAX / 2000)`. Negative values, including the native no-timestamp sentinel, and values beyond that bound invalidate the record without clamping. The independent source contract tests must cover negative finite values, the sentinel, NaN and infinities, the inclusive boundaries and a value beyond the upper boundary; none may advance source progress when invalid.

The helper also requires each playlist entry, discontinuity, source-frame serial and render serial to be in `1..INT64_MAX` before publication. Independent boundary tests must cover zero, `INT64_MAX`, and `INT64_MAX + 1` for each field, and verify that invalid records do not advance source progress. Native counters never wrap or reuse a value: `INT64_MAX` is an invalid exhaustion marker for discontinuity and source serials, while render serial can reach `INT64_MAX` once and later observations are invalid. A retained earlier frame may still redraw with its earlier source stamp after a source or discontinuity counter exhausts; it cannot claim a new source serial, but global immediate invalidation of every in-flight or retained observation is not established. Rendering continues normally after exhaustion.

Loader behavior should be independently qualified on each supported OS and packaging mode. In particular, import thunks, symbol interposition, forwarded exports, static linkage or an unload race can make module identity unverifiable; fail closed rather than open a second library. The design follows the documented [Windows module-address lookup](https://learn.microsoft.com/en-us/windows/win32/api/libloaderapi/nf-libloaderapi-getmodulehandleexw), [Linux address lookup](https://man7.org/linux/man-pages/man3/dladdr.3.html), [Linux already-loaded object lookup](https://man7.org/linux/man-pages/man3/dlopen.3.html), and [Apple's archived loader documentation](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man3/dlopen.3.html). Confirm macOS behavior in the target SDK before treating it as qualified.
