## Exact blockers

1. The provider's `packages/ffmpeg.cmake`, `packages/libplacebo.cmake`, `packages/mpv.cmake` and `toolchain/mingw-w64.cmake` name Git repositories without immutable source commits. `UPDATE_COMMAND ""` prevents one later update step; it does not identify the initial clone. `packages/fast_float.cmake`, `packages/shaderc.cmake`, and `packages/vulkan.cmake` explicitly select moving `main` branches; `packages/glad.cmake` selects `glad2`. libplacebo replaces its bundled `glad` and `fast_float` directories with separately fetched trees. Each enabled source, transitive dependency, nested submodule, patch and archive therefore needs an independently verified immutable identity before a complete lock exists.
2. `toolchain/rustup.cmake` runs the network `sh.rustup.rs` installer with `--default-toolchain nightly`, then `rustup update`. The required Rust compiler, host bootstrap, Windows targets, package-manager metadata and checksums are not pinned. The provider's `scripts/autobuild.sh` also invokes `ninja update`. A locked adaptation must replace these paths with verified workspace-local inputs and prohibit implicit updates.
3. The actual selected dependency closure, host-tool bootstrap, CRT and compiler configuration, artifact dependency closure, and current playback feature baseline have not been established. For example, the historical FFmpeg recipe enables GPL and version 3, OpenSSL, libssh, SRT, libplacebo, multiple codecs, NVDEC/NVENC and AMF. These declarations are useful evidence, not proof of the features or license composition of the existing binaries or of a new build. The installed binaries and their dependency and feature manifests need independent comparison before equivalence can be claimed.

The historical recipe does pin the GCC 14.4.0 source archive with SHA-512 `725ed8bdd43ef1726ffe8b5e8615a13e247fac9575b7626ae013a2975d000ea213212dc414b2f2631ac4785c1c8beca85555222faf9904d3b2fa6a3807a83a15`. This is one input, not a complete toolchain lock. Dated candidate Git revisions for FFmpeg, libplacebo and mingw-w64 are recorded in `provider-candidates.json` as investigation leads only; the recipe and existing archives do not prove those candidates were used together or are compatible.

## Static catalog and graph limits

`provider-input-catalog.json` records all 106 declared package recipe files, their exact provider blob IDs and source SHA-256 values, original source lines, source directives and lexical dependency sections. It also records 59 retrieved support files, including the provider's own patches, bootstrap files and workflows. Each downloaded source was checked against its Git blob ID before cataloging. `.gitmodules` is absent from this provider tree; that does not establish whether any subsequently fetched dependency has submodules. The 85,305-byte `cmake/CMake-v3.31.6-Modules-ExternalProject.zip` was not retrieved: the tree identifies its Git blob as `6136d2580000d235f1d6024793eb68eb376aaf67`, but its archive SHA-256 remains unverified. `cmake/download_externalproject.cmake` also downloads `ExternalProject.cmake` from a tag URL without a recorded content digest during configuration.

The catalog's lexical traversal from `mpv` reaches 84 declared package names. It is **not** an evaluated CMake dependency closure: conditions, dynamic variables, helper-created targets and toolchain dependencies remain unresolved. The catalog identifies the dependency-section expressions by path and line. In particular, `packages/ffmpeg.cmake` line 2 contains `${ffmpeg_x265}`, `${ffmpeg_uavs3d}` and `${ffmpeg_davs2}`; the x86-64 branch of `cmake/packages_check.cmake` sets the latter two to `uavs3d` and `davs2`, while `packages/x265.cmake` selects `x265-8+10bit` for x86-64 and defines additional helper targets. Those relationships still require full configuration analysis rather than treating the 84-name set as a complete lock.

The provider's root `CMakeLists.txt` declares CMake 3.19 minimum, Meson 1.3.0 minimum, Ninja as the supported generator, default target `x86_64-w64-mingw32` and default `GCC_ARCH=x86-64`. The GCC workflow contains an `x86-64-v3` conditional, but its displayed matrix at the pinned revision lists only `x86_64`. Its `ubuntu-latest` runner, `ghcr.io/shinchiro/archlinux:latest` container, `actions/checkout@main`, downloads, and update steps are not immutable and are not an authorized workstation execution path. The mingw-w64 CRT recipe declares `--with-default-msvcrt=ucrt`; the Rust bootstrap selects nightly. GCC 14.4.0 and binutils 2.45.1 source archive SHA-512 values are recorded in their corresponding cataloged files, but the complete compiler bootstrap, host tools and target dependency closure are not locked.

## Proposed artifact manifest, not an artifact or lock

`proposed-artifact-manifest.schema.json` specifies a reviewable v1 shape, requiring a separately trusted input-lock digest, producer identities, both CPU variants, DLL and MSVC import-library hashes, headers, bundled dependencies, system imports, feature declarations and public/private export lists. It contains no manufactured artifact hashes and does not assert that a producer or validator exists. The schema requires the standard render export and versioned private bridge export, but the complete required public export set must be derived from the actual application and MpvQt imports and qualified dynamic symbol lookups, not inferred from those two names.

A future validator must independently authenticate the selected input-lock and producer identities, verify schema and unique canonical contained paths without reparse escapes, compare every artifact's size and SHA-256, inspect the actual PE machine type and import/export tables, compare the MSVC import library against the exact corresponding DLL exports, and compare the bundled and operating-system dependency closure against the approved target policy. It must verify required codec, hardware decode, network and TLS feature evidence for both variants and reject `-march=native`, a missing fallback, stale files, mismatched headers, or a missing bridge. Manifest declarations alone cannot establish these facts. The producer must produce the manifest from verified outputs and bind it to the selected lock; no existing consumer has yet been changed to enforce this proposal.

## Required locked adaptation and consumer boundary

Resolve one complete feature-preserving source and host-tool closure, including licenses, archive hashes and bootstrap provenance; configure baseline x86-64 first and x86-64-v3 second from identical inputs with explicit target differences and no `-march=native`. A later authorized cross-build must use workspace-local pinned inputs and target-and-lock-keyed caches, never an implicit update. Its manifest must bind source, patch, toolchain, configuration, both DLLs, headers, import libraries, dependency closure and public/private export lists. Both variants must export the versioned bridge and required public mpv functions.

The current `dev/windows/setup.bat` accepts an existing DLL based on existence, `dev/windows/ci-mpv.ps1` consumes prebuilt archives, and `CMakeModules/CompleteBundleWin.cmake.in` treats the fallback DLL as optional. They do not enforce the required future custom-artifact identity or verify the generated MSVC import library against actual exports. Until a real artifact manifest and its producer are specified together, these paths are unchanged; their present behavior is not bridge-capability evidence. A complete integration must fail closed on stale, absent or mismatched primary and fallback artifacts and exercise both loader branches during separately authorized Windows acceptance.
